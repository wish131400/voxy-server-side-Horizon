## 1. 已修复：范围证明可能读取另一求值体积的角点

位置：`tools/rust/vss-native-core/src/density/modern_range.rs` 的插值节点范围判断。

插值求值和完整单元查询原本会同时匹配单元坐标及 `ModernVolume`。但标量范围查询的回读路径只匹配单元坐标。两角点优化通常不填写完整的 `modern_cells`，因此旧的完整单元仍可能留在缓存中。

当嵌套插值先经过体积求值，再经过标量地表搜索时，同一坐标的两种输入体积可以产生不同的 FP32 舍入。其后如果跟着窄区间分支，一个 ULP 就足以改变密度符号。范围判断若使用旧体积角点，会把存在实体的区间证明为空，导致搜索跳过它。

隔离复现使用外层 4×8 插值、内层 6×3 插值，以及从 `-0.13` 到 `0.87` 的纵向梯度：

- 在 Y=8，同一内层值分别为 `0.08600001`（`0x3db020c6`）和 `0.08600002`（`0x3db020c7`）。
- 旧体积缓存的八角点全为 -1。
- 原范围判断给出约 `[-1.0000076294, -0.9999923706]`。
- 标量实际在 Y=9 为 `0.75`，该段最高正密度位置为 Y=11。

修复为同时匹配 `base` 和本次推导的 `ModernVolume`。缓存不匹配时返回未知范围，由正常密度求值继续搜索。没有放宽空域证明，也没有改变噪声精度。

新增回归 `scalar_surface_search_rejects_corners_from_a_different_volume`，同时核对实际高度搜索和范围包围。修复后的隔离源码通过 16 项现代密度检查，以及现代点缓存和逐块下降地表搜索的 2 项集成检查。后者包含 70,800 次缓存与递归逐位对照。

这证明了一个确定的错误路径；尚未用实玩现场确认它对应哪一处可见缺块，也不将它解释为所有加载迟缓的原因。

## 2. 有稳定收益：噪声取整的 CPU 指令分支

位置：`tools/rust/vss-native-core/src/noise/modern.rs` 的 `Noise::sample`、octave 循环和 `ImprovedNoise::modern_sample`。

正式 Windows 库采用通用 x86_64 目标。对同一优化配置导出汇编后，默认现代噪声核有多处 `callq floor`，没有直接取整指令。隔离候选在运行时确认 SSE4.1 后进入专用函数，并使 octave 循环和内核内联到该目标；对应路径生成 `roundsd $9`，保留通用 CPU 回退。

此处使用的是精确的标量取整指令，并未实现多列 SIMD。没有启用 FMA、fast-math，没有把坐标降成 FP32，也没有更换梯度累加顺序。完整函数中存在多个分支和两个模式，汇编的静态调用位置数量不能当成一次查询的实际调用次数。

| 同轮输入 | 间距 | 正式库 ms | SSE4.1 候选 ms | 耗时下降 |
| --- | ---: | ---: | ---: | ---: |
| 主世界 | 1 | 12.006 | 10.976 | 8.6% |
| 主世界 | 4 | 68.180 | 60.096 | 11.9% |
| 主世界 | 16 | 80.530 | 71.440 | 11.3% |
| 主世界 | 64 | 82.354 | 70.825 | 14.0% |
| 末地 | 4 | 24.805 | 19.411 | 21.7% |
| 末地 | 16 | 39.940 | 32.366 | 19.0% |
| 下界 | 1 | 6.511 | 6.460 | 0.8% |
| 下界 | 16 | 12.354 | 10.702 | 13.4% |
| 主世界部分缓存 | 4 | 50.932 | 44.464 | 12.7% |

主世界间距 4 的反序复测为 `68.433 → 59.505 ms`，下降 13.0%；负坐标、种子 -917 为 `68.825 → 58.439 ms`，下降 15.1%。下界间距 1 的差别接近噪声，不能把所有场景都写成相同收益。

单独强制内联的控制组在正序主世界间距 4 为 `68.180 → 64.902 ms`，SSE4.1 候选再到 `60.096 ms`。因此总收益同时包含内联和指令选择；不能全部归因于消除 `floor` 调用。

候选通过：

- 60,432 次专用路径、直接通用路径和运行时入口的逐位比较，覆盖四种种子、坐标周期边界、负坐标、取整边界和带 smear 的混合噪声。
- 15 项现有现代密度检查，包含实际原版三维度的标量、体积和基础列参考，以及 Tectonic、Lithostitched、非有限值和嵌套网格检查。
- 上表各组及反序、负坐标组的完整输出校验。

这些检查验证了本机专用路径和直接调用的通用路径，没有在实际缺少 SSE4.1 的旧机器上启动验证，也没有测试其他四个平台的性能。ARM 平台的取整指令与 Windows 通用 x86_64 不同，不能照搬这一收益结论。

候选 DLL SHA256：`07cd00246f73985c16f814f5d0a6984b8b38c3475eff331aa77dd011129f0efc`。

### ARM64 补充核查

Rust 的 Linux AArch64 和 macOS AArch64 目标默认均启用 NEON 能力。反汇编现有两个 ARM64 发布库，均能看到直接取整的 `frintm` 指令。进一步对当前源码进行 Linux AArch64 交叉编译并导出汇编，现代 `Noise::sample` 已包含直接取整指令，没有调用 `floor` 的分支。因此不能把 Windows 通用 x86_64 的取整优化收益直接套给 ARM，重复添加 `target_feature(neon)` 也不足以产生相同收益。

ARM 后续更值得测量的是同模式多个采样点的批量计算，以及共用的局部角点索引和缓存复用。NEON 可并行处理四个 FP32 或两个 FP64，但噪声置换表的间接读取、密度分支和高度搜索会限制向量利用率；仍需保留每个点的梯度、octave 累加顺序，避免 FMA 改变结果。本次只完成构建配置和指令审查，没有 ARM 真机计时，也没有新增 ARM 专用执行路径。审查数据保留在忽略的 `external/performance/20261031-arm-noise-audit/`。

## 3. 有收益但还需完善：小体积角点用数组索引

现代角点缓存当前以 `(输入节点、坐标、完整求值体积)` 为哈希键。隔离候选对总格点数不超过 4,096 的体积改用按节点、体积区分的数组；其余路径仍使用哈希表。递归返回后也重新核对体积，避免把结果写到递归期间替换的数组中。

单独候选在主世界间距 4 的两组结果为：

- 正序 `73.090 → 67.639 ms`，下降 7.5%。
- 反序 `70.245 → 65.069 ms`，下降 7.4%。

其他间距收益较小。这个结果支持改进局部角点访问，但不支持无条件把所有缓存改成数组。

| 主世界正坐标 | 1 | 11.847 | 10.374 | 12.4% |
| 主世界正坐标 | 4 | 67.960 | 57.000 | 16.1% |
| 主世界正坐标 | 16 | 80.978 | 67.576 | 16.6% |

组合候选 DLL SHA256：`0594bde0a622797c73638a19618d9eca9f9fdf91ed313a454ae28bc1bc94a01a`。

## 4. 没有足够收益的候选

| 隔离修改 | 实测结果与决定 |
| --- | --- |
| 按插值节点缓存体积推导 | 主世界间距 4 约省 2.3%，大间距约 1.1%–1.2%；暂不增加生产状态 |
| 现代节点单独拆通用求值入口 | 间距 4 反而慢约 1.3%，大间距省约 2%；没有稳定整体收益 |
| 提前将梯度表转换为 FP32 | 各间距约在正负 2% 内变化；暂不采用 |
| 仅为昂贵现代节点保留横向缓存 | 间距 4 约省 0.4%，间距 16、64 慢约 1.4%、1.8%；直接取消便宜包装的缓存并不更好 |
| 在 SSE4.1 候选中改写八梯度数组循环 | 一组间距 16 省约 5.5%，间距 4、64 几乎不变；没有再扩大实施范围 |

## 5. C2ME 的可借鉴点和剩余方向

复核固定提交 `65fe39997e1b531119104dfe42ca99329ede57f8` 的三个文件：

- [BytecodeGen](https://github.com/RelativityMC/C2ME-fabric/blob/65fe39997e1b531119104dfe42ca99329ede57f8/c2me-opts-dfc/src/main/java/com/ishland/c2me/opts/dfc/common/gen/jvm/BytecodeGen.java) 为 AST 节点生成单点和批量方法，常量直接生成，复用已有节点方法。这与现有 Rust 的节点合并、别名消除和递归求值仍有区别。仅把现代节点入口拆开，实测不能替代这项工作。
- [Cache2D](https://github.com/RelativityMC/C2ME-fabric/blob/65fe39997e1b531119104dfe42ca99329ede57f8/c2me-opts-dfc/src/main/java/com/ishland/c2me/opts/dfc/mixin/MixinChunkNoiseSamplerCache2D.java) 在此接口上复用上一 X/Z 值，批量查询直接报告未命中。其价值在于契合访问模式，不能据此推出扩大缓存必定更快。
- [CacheOnce](https://github.com/RelativityMC/C2ME-fabric/blob/65fe39997e1b531119104dfe42ca99329ede57f8/c2me-opts-dfc/src/main/java/com/ishland/c2me/opts/dfc/mixin/MixinChunkNoiseSamplerCacheOnce.java) 区分原有 NoiseChunk 状态与外部查询，批量复用核对实际坐标数组。这也说明缓存身份需要表达实际求值契约，不能只按位置命中。

下一步优先把噪声指令分支做成可发布实现，再完善有总预算的局部角点数组。更大的执行图编译应作为独立实验，在维持惰性分支、体积身份和浮点运算顺序的前提下比较；不能承诺照搬 DFC 就有固定倍数提升。
