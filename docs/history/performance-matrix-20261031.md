# Fabric 原生计算性能对照（2026-10-31）

[文档目录](../README.md) · [阶段记录](validation.md)

本轮覆盖八个 Fabric 目标及对应 Forge 1.20.1、NeoForge 1.21.1 的 Windows 发布库。确认并在源码修复 26.2 分段节点缺少取值范围造成的性能退化；修复库目前仅用于离线验证，尚未替换标准发布 JAR 或合包。其余七个旧 Fabric 发布包使用相同的旧 Rust 库，26.3 已使用上一轮按需坡度查询构建。

后续 `20261031-refinement-grid` 构建将该修复与缓存细化、26.3 末地搜索优化一并同步到八个标准 Fabric 目标。下文保留此次审查时的发布基线；最新改动和验证范围见[后续记录](refinement-grid-20261031.md)。

## 方法与边界

- 各 Fabric 发布库直接从对应标准 JAR 提取，各版本读取自己的官方世界生成资源。固定种子 0，固定平原群系，复用同一套方块属性，隔离地形和显示材质计算；并非各版本完整的生产环境快照。
- 每组启动独立 JVM，单线程执行七轮；每轮新建采样世界，在十六个分散区域查询 1,024 根柱。间距为 1、4、16、64 方块，轮次间反转间距顺序，表中为中位耗时。
- 计时覆盖 JNI 查询和完整十字段输出校验，世界初始化单列计时。再次查询同一位置验证内存缓存；前后完整记录校验值必须一致。
- 所有目标使用相同 JDK 25 包装程序；没有比较 Java 17、21、25 游戏运行时差异。没有测量 Java 植被、主线程调度、缓存文件恢复、GPU、体素发布或 FPS。
- 每档查询柱数相同，但间距改变了覆盖面积和局部复用程度，因此这些数据不能直接当作游戏内各档 LOD 的完成时间。
- 最初额外网格诊断误用了不支持的 16、64 间距，接口拒绝的结果全部排除。后续部分缓存网格只用支持的 1、4 间距。

## 26.2 根因与修复验证

26.2 用 `interval_select` 表达部分洞穴噪声。解析器已有对应的 `Node::Select` 求值，但 `ColumnPlan` 没有编译其有限取值范围，导致包裹它的整个插值节点被标为未知。位于 X/Z 网格点上的采样因此不能使用已验证的两个角点路径，转而读取八个角点。只增加线程不能消除这些重复计算。

使用同一发布库逐项替换输入，换回旧版最终密度外层、材质规则或单个密度资源均不能消除退化；换回旧密度注册表恢复正常，把新注册表放进旧设置又能复现。直接使用上一轮最新核心处理 26.2 输入仍约需 216.64 ms（间距 16），说明问题并非仅由旧发布库造成。

修复为取所有分段结果（含默认分支）的范围并集，任一分支无有限范围则保留未知回退。阈值比较、具体采样公式和缓存遍历规则不变。新增检查验证分支边界、负坐标、两种插值顺序、后续非网格点访问和非有限分支回退；实际证实正常路径使用两个角点、回退路径保留八个角点。

## 与 Forge / NeoForge 的同输入对照

同版本使用完全相同的输入文档和调用方式，间距 16、1,024 列的中位耗时如下。两份 Forge/NeoForge 发布库的 DLL 校验值相同。

| 匹配版本 | 旧 Fabric 发布库 ms | Fabric 候选库 ms | 对应加载器发布库 ms |
| --- | ---: | ---: | ---: |
| 1.20.1 / Forge | 81.34 | 70.54 | 71.82 |
| 1.21.1 / NeoForge | 79.90 | 73.06 | 72.60 |

这两组核心耗时已经接近，不能推出游戏内的完整细化和发布速度相同。26.3 使用新的浮点生成图、材质体系和插值设置，不能把它与 1.21.1 的不同输出直接当作同画面吞吐倍率。

## 继续审查的差距

部分缓存恢复时，自适应网格尝试在复杂地形上可能得不偿失。模拟 Java 已保留 16/64 点、Rust 缓存尚冷的情形，实际只缺 48 点；网格入口先查询边界和中心探针，拒绝插值后再补齐缺失位置，部分探针位于 Java 已保留区域。候选库 26.3 在间距 4 下，直接查询缺失点为 64.69 ms，网格入口为 78.60 ms，多约 22%；26.2 为 47.84 / 57.59 ms，多约 20%。八版本两档间距的两条入口分别做前后校验，结果一致。此结论针对冷缓存及该缺失形状，需要继续测量平坦场景成功插值时的收益，不能据此全局禁用网格入口。

26.3 末地仍有明显差距。源码中通用地形查询工作区使用 4×8 的逻辑单元，原版末地插值节点使用 8×4；跨节点自身网格的区间会回退继续采样。该差异是后续应测量的候选原因，尚未证明贡献比例。仅补末地噪声有限范围的对照没有稳定收益，实验已撤回，未计作优化。

26.3 的 Java 区域入口在 GPU 未返回结果时仍分配区域坐标、映射和高度数组，并会在内部窗口再次检查缓存。这是待测的分配成本，当前数据不足以判断其相对权重。生物群系附加查询、Java 植被和最终写入 Voxy 的成本也不在本轮原生表格内。

## 可重复运行

使用 `tools/verification/native_performance_matrix.py`，给每个 `--case` 传入标签、发布包中提取的当前平台原生库和对应的有效世界生成 JSON。指定 `--java-home`、`--output`，可选 `--seed`、`--origin`、`--steps`、`--rounds`、`--mode`。工具分别启动 JVM，输出输入和库的 SHA-256、原始记录、初始化/冷查询/缓存查询中位值，并检查重复查询及轮次间的完整记录校验。

`points` / `grid` 每轮 1,024 列；`partial-points` / `partial-grid` 使用相同缺失形状，每轮只消费 768 个缺失列。网格入口只允许间距 1..4。跨版本输出可以不同，只对同版本修改前后比较校验值；工具不会把不同文档的结果自动判作一致。原始下载资源、运行记录和本机路径保存在忽略目录，不作为版本库测试夹具提交。
